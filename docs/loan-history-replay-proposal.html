Loan-history reverse-replay around the ad-funding adjustment

Right now, the ad-funding API runs against whatever balance the loan happens to have at the moment of the call. The new flow runs it against the loan's end-of-last-month balance instead — back out this month's transactions before the call, run ad-funding, replay them after. Same Excel input drives it.

The change at a glance

Same Excel input, same target tables, same lender-portfolio refresh at the end. Three new pieces slot in between to bracket the ad-funding call.

Today
Excel → ad-funding → portfolio One ad-funding API call per loan against today's balance.
Proposed
Excel → reverse → ad-funding → replay → portfolio Ad-funding API sees the loan as it stood on the 1st of the month; current-month txns layered back on after.
Blast radius
Zero on the existing flow PL_LOAD_ADD_FUNDINGS_DEV stays untouched. New pipelines parallel it.

03

Inside the new orchestrator · per-loan

For each loan, PL_CHILD_REVERSE_REPLAY_DEV runs three phases. Phase 2 calls the existing ad-funding child unchanged; phases 1 and 3 are new AddLoanHistory calls.

1
NEW · REVERSE
Back out this month
For every txn with DateRec in the current month: POST AddLoanHistory with all To* amounts negated. RecID + status written back to the staging row.
2
REUSED · AD-FUNDING
Run the adjustment
Once per loan. Calls the existing PL_CHILD_POST_ADD_FUNDINGS_DEV with the same parameters. Loan balance at this moment equals end-of-last-month.
3
NEW · REPLAY
Re-apply this month
For every txn whose reversal succeeded: POST AddLoanHistory with the original signs. Loan returns to its original state plus the ad-funding adjustment.

New pipelines & what they do

PipelineRole
PL_LOAD_ADD_FUNDINGS_WITH_HISTORY_DEV new Entry point. Mirrors PL_LOAD_ADD_FUNDINGS_DEV through the validate step; then inits a batch id, runs history load, runs the new orchestrator, archives the file.
PL_LOAD_LOAN_HISTORY_DEV new Lookup distinct loans from vw_loans_to_process_history; ForEach → child.
PL_CHILD_LOAD_LOAN_HISTORY_DEV new One loan. WebActivity GET /LSS.svc/GetLoanHistory/{loan}, then SP pr_load_loan_history_replay parses, filters to current month, inserts into loan_history_replay_stage.
PL_POST_ADD_FUNDINGS_WITH_HISTORY_DEV new Orchestrator. Lookup vw_post_fund_adjustment_with_history, ForEach loan → reverse-replay child. After loop: existing portfolio loader.
PL_CHILD_REVERSE_REPLAY_DEV new Per-loan worker that drives the three phases shown in Figure 2.
PL_CHILD_POST_ADD_FUNDINGS_DEV reused Existing ad-funding API caller — called once per loan from phase 2 of the new child.
PL_LOAD_FUND_ADJUSTMENT_LENDER_PORTFOLIO_DEV reused Existing lender-portfolio refresher — called once at the end of the orchestrator, as today.
05

SQL changes

One self-contained script in sql/loan_history_replay.sql. No changes to existing tables, views, or procs — everything is additive and idempotent.

ObjectPurpose
loan_history_replay_stage table One row per filtered TMO transaction per run. Holds the original txn fields plus 3 audit blocks (reversal · ad-funding · replay) — each with status, RecID, response JSON, timestamp.
vw_loans_to_process_history view Distinct loans from fund_adjustment_detail joined to the new GET_LOAN_HISTORY entry in api_master. Drives the outer ForEach of PL_LOAD_LOAN_HISTORY_DEV.
vw_post_fund_adjustment_with_history view Wraps existing vw_post_fund_adjustment and adds three columns for the AddLoanHistory endpoint + headers.
vw_loan_history_reverse_queue view For each unprocessed row, builds the full AddLoanHistory JSON body inline with negated To* values.
vw_loan_history_replay_queue view Same shape but filtered to reversal_status = 'PS' and built with original signs.
pr_init_replay_batch proc Returns a fresh RPL-yyyyMMddHHmmss batch id. Called once per pipeline run.
pr_load_loan_history_replay proc Parses GetLoanHistory JSON with OPENJSON, applies current-month filter, maps PayMethod string → enum int, inserts into staging.
pr_update_loan_history_phase proc Single-row status writer — sets {phase}_recid/status/response/posted_on for phase ∈ {reverse, adfund, replay}.
pr_fanout_adfund_response proc Writes the ad-funding outcome to every txn row for the (batch, loan) so the audit table tells a complete story per row.
api_master rows inserts Two new rows: GET_LOAN_HISTORY and POST_ADD_LOAN_HISTORY. Token + Database copied from the existing POST_ADD_FUNDINGS row; URL derived via REPLACE.

Importing the bundle

A zip is available at dist/loan-history-replay-bundle.zip. It contains the 5 new pipeline JSONs (in ADF Studio "Code view" format), the SQL DDL, and a short README. The two reused pipelines aren't included — they're already in the factory.

Bundle contents
  • sql/loan_history_replay.sql — run this first against cal_bi_analytics_dev. Idempotent, safe to re-run.
  • pipeline/ — five JSONs to paste into ADF Studio (order matters: children before their parents).
  • README.txt — same steps, in plain text.
StepWhat to do
1 Run sql/loan_history_replay.sql against cal_bi_analytics_dev (SSMS / Azure Data Studio / sqlcmd — whichever's handy).
2 Open ADF Studio for adf-cal-dwh. Confirm PL_CHILD_POST_ADD_FUNDINGS_DEV and PL_LOAD_FUND_ADJUSTMENT_LENDER_PORTFOLIO_DEV already exist — the new pipelines reference them.
3 For each JSON in the bundle (children first, parents last — see order in the next row):
  • Author tab → + → Pipeline → New pipeline.
  • Click the { } icon at the top-right (Code view).
  • Paste the entire JSON file contents. Click OK.
  • Click Save.
4 Import order (each row references the row above):
  1. PL_CHILD_LOAD_LOAN_HISTORY_DEV
  2. PL_LOAD_LOAN_HISTORY_DEV
  3. PL_CHILD_REVERSE_REPLAY_DEV
  4. PL_POST_ADD_FUNDINGS_WITH_HISTORY_DEV
  5. PL_LOAD_ADD_FUNDINGS_WITH_HISTORY_DEV  top-level
5 Click Publish all to commit everything to the factory.
6 Smoke-test: drop a 1-loan Excel in the source container, run PL_LOAD_ADD_FUNDINGS_WITH_HISTORY_DEV in Debug mode, then check loan_history_replay_stage — every row should have all three phase statuses populated.

If the paste-import flow ever feels tedious, the same JSONs can be dropped into the ARM template repo's pipeline/ folder and shipped via az deployment group create — same result.

07

When something fails

Best-effort: log it, keep going. No step short-circuits the loop — every outcome (success or failure) lands on the txn row so we can review afterward.

If this step fails…Recorded asWhat happens next
Reverse for txn T reversal_status='FAIL' T is excluded from the replay phase. Loan still proceeds to ad-funding.
Ad-funding for loan L adfund_status='FAIL' on all rows Replay still runs for rows where the reversal succeeded — loan returns to its original state. Operator reconciles ad-funding separately.
Replay for txn T replay_status='FAIL' Loan is now out of balance by T's amount. Pipeline still continues; manual fix required, visible immediately via the audit table.

09

Worth knowing

  • TMO URLs & creds — already in api_master. Two new rows added: GET_LOAN_HISTORY_BY_AN (with the usual #ACCOUNT_NO placeholder) and POST_ADD_LOAN_HISTORY. Both inherit Token + Database from the existing POST_ADD_FUNDINGS row, so no new secrets.
  • Negative To* values are accepted by AddLoanHistory — phase 1 posts the negated amounts directly, no separate reversal endpoint needed.
  • No trigger for now. Manual / on-demand in DEV. We'll figure out PROD scheduling after the first clean DEV run.
