# Pipeline: PL_LOAD_ADD_FUNDINGS_WITH_HISTORY_DEV
Date: 2026-05-20
Status: planned

## What it does

For each loan listed in the input Excel, the pipeline (1) pulls the loan's full transaction history from TMO via `GetLoanHistory`, (2) keeps only transactions whose `DateRec` falls in the current calendar month (1st → today), (3) posts a sign-flipped reversal entry for each such transaction via `AddLoanHistory`, (4) calls the existing ad-funding adjustment API once per loan, (5) replays each transaction with its original signs via `AddLoanHistory`, and (6) refreshes the lender portfolio. All step outcomes (RecIDs, statuses, raw API responses) are persisted to `loan_history_replay_stage` for review.

The net effect: the ad-funding API sees the loan as it stood at the start of the month; current-month transactions are layered back on after the adjustment.

## Load pattern

- Type: **per-loan, per-transaction** orchestration (no traditional delta/full split).
- Control table / view: `vw_post_fund_adjustment_with_history` (new — extends existing `vw_post_fund_adjustment` with TMO base URL + GetLoanHistory token + database). Drives the orchestrator's outer ForEach.
- Inner control table: `loan_history_replay_stage` — drives the per-loan reverse and replay ForEach passes.
- Batch key: `batch_id` (UUID generated by `pr_init_replay_batch`, stamped on `fund_adjustment_detail` rows and on `loan_history_replay_stage` rows).

### `PL_LOAD_LOAN_HISTORY_DEV`

- `LOOKUP_LOANS_TO_PROCESS`: `SELECT DISTINCT loan_account, tmo_base_url, loan_history_token, dbase_name FROM vw_loans_to_process_history WHERE batch_id = @batch_id`
- `ForEach1` (sequential): `EXEC PL_CHILD_LOAD_LOAN_HISTORY_DEV` per row.

### `PL_CHILD_LOAD_LOAN_HISTORY_DEV`

Parameters: `loan_account`, `batch_id`, `tmo_base_url`, `token`, `dbase_name`.

1. `CALL_GET_LOAN_HISTORY` — WebActivity `GET @{tmo_base_url}/LSS.svc/GetLoanHistory/@{loan_account}` with headers `Token`, `Database`. Retry 3, interval 30s.
2. `SET_VARIABLE_RESPONSE` — stringify `@activity('CALL_GET_LOAN_HISTORY').output` into `varjsonstring` (same pattern as existing `PL_CHILD_POST_ADD_FUNDINGS_DEV`).
3. `SCR_LOAD_LOAN_HISTORY_REPLAY` — Script activity calling `EXEC dbo.pr_load_loan_history_replay @loan_account=..., @api_response=@varjsonstring, @batch_id=...`. The proc parses JSON via `OPENJSON`, filters `DateRec` in `[DATEFROMPARTS(YEAR(GETDATE()), MONTH(GETDATE()), 1), CAST(GETDATE() AS date)]`, maps `PayMethod` string → enum int, and inserts rows.

### `PL_POST_ADD_FUNDINGS_WITH_HISTORY_DEV`

- `LOOKUP_POST_FUND_ADJUSTMENT_WITH_HISTORY`: `SELECT * FROM vw_post_fund_adjustment_with_history WHERE batch_id = @batch_id`. Returns one row per loan with: ad-funding `api_url`, `token`, `dbase_name`, `account_no`, `api_body`, plus `tmo_base_url`, `loan_history_token` (for AddLoanHistory).
- `ForEach1` (sequential): `EXEC PL_CHILD_REVERSE_REPLAY_DEV` per row, passing all params + `batch_id`.
- After ForEach: `EXEC_PL_LOAD_FUND_ADJUSTMENT_LENDER_PORTFOLIO_DEV` (existing).

### `PL_CHILD_REVERSE_REPLAY_DEV` — the core

Parameters: `loan_account`, `batch_id`, `tmo_base_url`, `loan_history_token`, `dbase_name`, `api_url`, `token`, `api_body`.

```
LOOKUP_TXNS_TO_REVERSE
   SELECT replay_stage_id, date_due, date_rec, pay_method_enum,
          principal, interest, late_charges, impound, broker_fee,
          lender_fee, reserve, other_paid, prepay_fee,
          charges_principal, charges_interest, unpaid_interest,
          loan_balance, reference
   FROM loan_history_replay_stage
   WHERE batch_id=@batch_id AND loan_account=@loan_account
     AND reversal_status IS NULL
   ORDER BY date_rec, replay_stage_id
   ↓
ForEach_Reverse (sequential)
   CALL_ADD_LOAN_HISTORY_REVERSE (WebActivity POST /LSS.svc/AddLoanHistory)
     Body: JSON object with negated To* amounts, SourceApp='AdfundReverse',
           Notes=concat('Reversal for ad-funding batch ', @batch_id)
     Headers: Token=@loan_history_token, Database=@dbase_name, Content-Type
     Retry 3, interval 30s
        ↓ (Succeeded or Failed — Script always runs)
   SCR_UPDATE_REVERSE_PHASE
     EXEC pr_update_loan_history_phase
       @replay_stage_id=..., @phase='reverse',
       @status=<PS|FAIL>, @recid=..., @response=<json>
   ↓
EXEC_PL_CHILD_POST_ADD_FUNDINGS_DEV  (reused — existing ad-funding child)
   Passes: api_url, token, dbase_name, account_no=loan_account, api_body
   ↓
SCR_FANOUT_ADFUND_RESPONSE
   UPDATE loan_history_replay_stage
   SET adfund_status='PS', adfund_response=<from activity output>,
       adfund_posted_on=GETDATE()
   WHERE batch_id=@batch_id AND loan_account=@loan_account
     AND reversal_status='PS'
   (If ad-funding failed: status='FAIL'; still proceeds to replay.)
   ↓
LOOKUP_TXNS_TO_REPLAY
   SELECT ... FROM loan_history_replay_stage
   WHERE batch_id=@batch_id AND loan_account=@loan_account
     AND reversal_status='PS' AND replay_status IS NULL
   ORDER BY date_rec, replay_stage_id
   ↓
ForEach_Replay (sequential)
   CALL_ADD_LOAN_HISTORY_REPLAY (WebActivity POST /LSS.svc/AddLoanHistory)
     Body: JSON object with ORIGINAL To* amounts, SourceApp='AdfundReplay',
           Notes=concat('Replay for ad-funding batch ', @batch_id)
        ↓
   SCR_UPDATE_REPLAY_PHASE
     EXEC pr_update_loan_history_phase @phase='replay', ...
```

WebActivity bodies are built using `@concat(...)` / `@string(json(...))` expressions referencing `@item().*` from the ForEach. Date fields are formatted with `@formatDateTime(item().date_rec, 'MM-dd-yyyy')`.

### View `dbo.vw_loans_to_process_history`

```sql
CREATE VIEW dbo.vw_loans_to_process_history AS
SELECT DISTINCT
    fad.loan_account,
    fad.batch_id,
    cfg.tmo_base_url,
    cfg.loan_history_token,
    cfg.dbase_name
FROM dbo.fund_adjustment_detail fad
CROSS APPLY (SELECT tmo_base_url, loan_history_token, dbase_name
             FROM dbo.tmo_api_config WHERE is_active = 1) cfg
WHERE fad.is_processed = 0;
```

(Assumes a config table `dbo.tmo_api_config` already exists or is added with the existing ad-funding URL/token. If the project keeps URLs in `vw_post_fund_adjustment` only, instead derive the base URL by stripping the ad-funding-specific path from `api_url`.)

### View `dbo.vw_post_fund_adjustment_with_history`

Extends `vw_post_fund_adjustment` with `tmo_base_url`, `loan_history_token`, `dbase_name` columns sourced the same way as above.

### Stored procs

- `dbo.pr_init_replay_batch(@batch_id_out UNIQUEIDENTIFIER OUTPUT)` — generates a UUID, stamps it onto `fund_adjustment_detail WHERE is_processed=0` (add a `batch_id` column to that table if missing — single ALTER TABLE), returns it.
- `dbo.pr_load_loan_history_replay(@loan_account VARCHAR(50), @api_response NVARCHAR(MAX), @batch_id UNIQUEIDENTIFIER)` — parses `$.Data[*]` with `OPENJSON`, filters by `DateReceived` in current calendar month, maps `PayMethod` string → enum, inserts into `loan_history_replay_stage`.
- `dbo.pr_update_loan_history_phase(@replay_stage_id BIGINT, @phase VARCHAR(10), @status VARCHAR(10), @recid VARCHAR(64), @response NVARCHAR(MAX))` — single-row update of the `{phase}_recid/status/response/posted_on` columns.

## Failure model — best-effort, log, continue

| Failing step | Recorded as | Next action |
|---|---|---|
| Reversal of txn T fails | `reversal_status='FAIL'`, response captured | Continue to next txn. T excluded from replay (filter requires `reversal_status='PS'`). Loan proceeds to ad-funding. |
| Ad-funding call fails | `adfund_status='FAIL'` on all rows for loan | Replay still runs for all rows with `reversal_status='PS'` — restores loan to original state. Operator reconciles ad-funding separately. |
| Replay of txn T fails | `replay_status='FAIL'`, response captured | **Loan is now out of balance by T's amount.** Pipeline still continues to next txn / next loan. Manual reconciliation required, surfaced via audit query. |

ForEach activities use default continuation (no aborting OnFailure). WebActivity failure routes via `dependencyConditions: ["Succeeded", "Failed"]` on the Script that records status, so the loop never short-circuits.
